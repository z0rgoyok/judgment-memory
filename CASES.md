# Кейсы

## 1. Таблица соответствия документа видения коду ядра

### Ситуация

Документ видения продукта содержит таблицу «Подтверждено в ядре»: слева требование, справа опора в коде.

| Требование | Опора в ядре |
| --- | --- |
| Явная зависимость работ | `task.relate kind: depends_on`; запуск ждёт `done` всех зависимостей (`scheduler/claim_run.py`, `has_capacity`); циклы отклоняются (`task_dependencies.py`) |
| Общий бюджет без параллельного перерасхода | проверка остатка и резерв в одной транзакции захвата (`claim_run.py`, `budget_service.py`); расход один раз на запуск (`usage UNIQUE(run_id)`) |
| Идемпотентность команд | `receipts UNIQUE(actor_id, request_key)` с хешем параметров (`execute_commands.py`) |

Рядом таблица «Требуется» с тем, чего в ядре нет, и слоем, который закрывает пробел до его появления.

Каждая строка первой таблицы — суждение класса `judgment`: человек или агент прочитал код и утверждает, что требование
им обеспечено. Документ хранит вывод и название файла. После правки `claim_run.py` строка остаётся в документе без
изменений, и никто не узнаёт, что она перестала быть правдой. Таблица «Требуется» устаревает в другую сторону: ядро
получает нужную возможность, а строка продолжает утверждать, что её нет.

### Запись

```yaml
kind: doc-claim
question: vision-backing@v1
class: judgment
claim: "Запуск работы ждёт состояния done у всех зависимостей; цикл зависимостей отклоняется"
anchors:
  - {kind: doc,  path: docs/VISION.md, section: "Подтверждено в ядре#явная-зависимость", text_hash: ...}
  - {kind: code, path: scheduler/claim_run.py, symbol: has_capacity, body_hash: ...}
  - {kind: code, path: scheduler/task_dependencies.py, symbol: reject_cycle, body_hash: ...}
  - {kind: schema, path: schema.sql, object: task_relations, ddl_hash: ...}
verdict: backed                        # backed | gap
proof: tests/scheduler/test_claim_waits_for_dependencies.py
owner: "автор редакции документа"
tier: reviewed
origin: "редакция документа видения от 2026-09-22"
```

Строка таблицы «Требуется» получает ту же форму с `verdict: gap` и якорем только на документ; при появлении кода
проверка находит символ, который закрывает пробел, и требует обновить строку.

### Что даёт

| Событие | Раньше | С записью |
| --- | --- | --- |
| Правка `has_capacity` | строка документа молчит | запись `stale`, документ помечен к пересмотру, `proof` перезапускается |
| Правка раздела документа | код ничего не знает | запись `stale`, требование сверяется с кодом заново |
| Ядро получило возможность из «Требуется» | строка утверждает пробел | `gap` с найденной реализацией краснеет до правки документа |
| Новая редакция документа | таблица переписывается руками | генерируется из записей: `backed` в одну таблицу, `gap` в другую |

Таблицы соответствия перестают быть текстом и становятся проекцией памяти суждений. Деление документа на «Ядро
сегодня» и «Требуется» совпадает с делением модели на описательную и нормативную части.

### Проверки gate

1. Свежесть обоих якорей.
2. `proof` проходит для каждой записи `backed`.
3. Для каждой записи `gap` детектор по имени возможности не находит реализации в коде.
4. Сгенерированные таблицы совпадают с текстом документа.

### Порог входа

Кейс подходит документу, который утверждает соответствие между собой и кодом: видение, ADR, таблица трассировки
требований, описание API. Документ без ссылок на код записей не получает.
