# Память суждений о коде

Модель нормативной контентно-адресуемой памяти команды людей и агентов. Она обобщает baseline
[slopo](https://github.com/z0rgoyok/slopo): вердикт о дублировании становится частным случаем суждения о коде.

## 1. Идея

Суждение о коде стоит дорого: его выносит человек, ревьюер или LLM. Модель хранит каждое суждение как запись с
четырьмя свойствами:

- **мета-уровень** — запись содержит решение о коде; сам код живёт в Git;
- **контентная адресация** — ключ записи строится из хешей кода, о котором она сделана, и версии заданного вопроса;
- **самоинвалидация** — изменение кода меняет хеш, и запись перестаёт совпадать ровно в момент изменения факта;
- **исполняемость** — gate читает записи и блокирует merge при нарушении.

Итог: кэш дорогих суждений. Ключ — хеш входов и версия вопроса. Значение — вердикт с автором, причиной и уровнем
проработки.

### 1.1. Цельная модель

Память, исполняемая спецификация и код образуют одно целое. Деление между ними задаёт направление чтения, границ
хранения оно не создаёт:

| Точка входа | Кто читает | Что видит |
| --- | --- | --- |
| Спецификация | владелец, аналитик | требования, инварианты, статус доказанности |
| Память | ревьюер, агент | суждения, решения, препятствия, отвергнутые попытки |
| Код | исполнитель, компилятор | символы с прикреплёнными инвариантами и владельцами |

Каждая запись принадлежит всем трём сразу: инвариант — утверждение спецификации, суждение о его выполнении и якорь
на код. Спецификация, матрица трассируемости, документ видения и baseline gate — проекции одной памяти. Хеши держат
их согласованными всегда: ни одна проекция не может утверждать то, что перестало быть правдой в другой.

Один носитель служит людям и машинам. Человек читает `statement`, `reason`, `origin`. Машина читает якоря,
`holds_by`, `status` и исполняет gate. Поля не дублируют друг друга: текст для человека прикреплён к тем же хешам,
которые проверяет машина.

## 2. Запись суждения

```yaml
question: duplication/semantic@v3     # вид суждения и версия рубрики
anchors:                              # о каком коде сделано суждение
  - path: orders/domain/use_cases/close_order.py
    symbol: CloseOrderUseCase.__init__
    body_hash: 88dac957...            # точный хеш тела
    ast_hash: 749ce3da...             # нормализованный AST без форматирования и локальных имён
verdict: accepted-existing-debt
reason: "Исторический baseline; индивидуально не разобран"
owner: "кто принял решение"
tier: loose                           # loose | reviewed | confirmed
evidence: ["commit", "ссылка на ревью"]
origin: "откуда взялась запись: находка ревью, требование, первичный baseline"
status: active                        # active | stale
```

`tier` фиксирует степень проработки. `loose` означает «принято оптом», и следующий участник видит, какие вердикты
проверены индивидуально.

## 3. Якоря и устаревание

Якорь ступенчатый: `body_hash`, затем `ast_hash`, затем путь символа.

| Совпало | Состояние записи |
| --- | --- |
| `body_hash` | `active` |
| только `ast_hash` | `active`, хеш тела обновляется автоматически |
| только путь символа | `stale`, запись уходит в очередь перепроверки с сохранением причины и автора |
| ничего | запись удаляется при следующей синхронизации |

Суждение может зависеть от нескольких участков кода: утверждение «функцию вызывают только из use case» зависит от самой
функции и от всех вызывающих. Ключ такой записи — хеш множества входов, по образцу ключей кэша сборочных систем.
Изменение любого входа переводит запись в `stale`.

Версия вопроса входит в ключ. Рост версии рубрики сбрасывает все вердикты по этому вопросу.

### 3.1. Якорь на любой артефакт

Якорь указывает на любой артефакт с адресуемым содержимым: символ кода, раздел документа, элемент BPMN, таблицу схемы,
запись другого суждения. Каждая сторона связи получает свой якорь:

```yaml
anchors:
  - {kind: doc,  path: docs/VISION.md, section: "Подтверждено в ядре#явная-зависимость", text_hash: ...}
  - {kind: code, path: scheduler/claim_run.py, symbol: has_capacity, body_hash: ...}
```

Инвалидация симметрична: изменение любой стороны переводит запись в `stale`. Правка раздела документа сбрасывает
суждения, завязанные на этот раздел, так же, как правка функции сбрасывает суждения о ней. Кейс: [CASES.md](./CASES.md#1).

## 4. Виды суждений

| Вид | Что хранит |
| --- | --- |
| `duplication/*` | принятое дублирование, exact и semantic кластеры |
| `layering` | принятое нарушение границ слоёв |
| `security-triage` | разбор находки: ложное срабатывание и его причина |
| `flaky-test` | карантин нестабильного теста |
| `intentional` | намеренно медленное или необычное место |
| `invariant` | проверяемое утверждение спецификации с обязательством доказательства, раздел 11 |
| `production-fact` | подтверждённый факт выпуска поведения в production |
| `doc-claim` | утверждение документа о коде с якорями на обе стороны, [CASES.md](./CASES.md#1) |
| `review-verdict` | вердикт ревью по срезу кода и рубрике |
| `rejected-attempt` | отвергнутая попытка: что пробовали и почему откатили |
| `check-verdict` | вердикт детерминированной проверки по срезу и toolchain, раздел 9 |
| `known-obstacle` | известное препятствие исполнения и способ его обхода, раздел 9 |
| `process-element` | извлечённый из кода элемент процесса, раздел 10 |
| `concept` | владелец доменного вопроса, раздел 5 |
| `decision` | формальное бизнес-правило, раздел 6 |

`review-verdict` даёт инкрементальное ревью: повторный проход читает только код со сменившимся хешем.

`rejected-attempt` экономит больше остальных видов в агентной разработке: агенты склонны повторно предлагать одно и то
же объединение или рефакторинг.

## 5. Концепт и мета-владелец

Концептуальное дублирование — несколько мест по-разному отвечают на один доменный вопрос. Тела функций непохожи, поэтому
детектор сходства его пропускает. Кластер концепта определяется как множество мест, отвечающих на один вопрос;
принадлежность к нему задаёт детектор примитивов.

```yaml
kind: concept
concept: worker-role-active-at
question: "Активна ли роль сотрудника в момент T?"
owner_symbol:
  path: organizations/roles/activity.py
  symbol: is_worker_role_active_at
  body_hash: ...
contract: "вход — момент времени в UTC и подразделение; часовой пояс определяет только владелец"
primitives:
  - fields: [WorkerRole.start_date, WorkerRole.end_date]
  - orm_lookups: [start_date__lte, end_date__gte, end_date__isnull]
  - clock: [date.today, timezone.now, timezone.localdate]
sites:
  - {symbol: ..., role: owner}
  - {symbol: ..., role: delegates}
  - {symbol: ..., role: accepted-divergence, reason: ..., tier: reviewed}
proof: tests/test_role_activity_agreement.py
origin: "системная находка независимого ревью"
```

Правило gate: каждое место, трогающее примитивы концепта, имеет одну из трёх ролей — владелец, делегат (вызывает
владельца) или принятое исключение с причиной. Новое место без роли блокирует merge. Число самостоятельных решений по
концепту может только уменьшаться.

Детекторы по возрастанию цены:

1. **Доступ к полям** — AST-проход по чтению полей модели и ORM-ключам фильтров.
2. **Источник времени** — вызовы системных часов вне владельца концепта «бизнес-дата».
3. **Тип параметра** — функция проверки активности, принимающая `date`: часовой пояс выбрал вызывающий код.
4. **LLM-классификатор с мемоизацией** — «решает ли функция концепт C?», ответ кэшируется по `body_hash` и версии
   концепта; оплачиваются только изменённые функции.

Концепт заводится из находки ревью: ревьюер помечает расхождение как системное, запись с детектором делает gate
красным, исполнитель сводит места к владельцу, запись остаётся в репозитории с полем `origin`.

## 6. Решение

Бизнес-правило записывается в семантике DMN и хранится в YAML. Формальная запись требует назвать все входы. Правило вида

```python
def is_active(self, check_date=None):
    if check_date is None:
        check_date = date.today()   # дата сервера — скрытый вход
```

получает явные входы и граф зависимостей:

```yaml
kind: decision
decision: worker-role-active-at
version: 1
inputs:
  instant: datetime(UTC)
  division_tz: tz
  period: {start: date, end: date | null}
requires: [division-business-date]
logic: |
  d = division-business-date(instant, division_tz)
  period.start <= d and (period.end is null or d <= period.end)
examples:
  - {instant: 2026-03-31T15:30Z, tz: Asia/Vladivostok,   start: 2026-04-01, end: null, expect: true}
  - {instant: 2026-03-31T15:30Z, tz: Europe/Kaliningrad, start: 2026-04-01, end: null, expect: false}
  - {instant: 2026-04-01T09:00Z, tz: Europe/Moscow,      start: 2026-04-01, end: 2026-04-01, expect: true}
implemented_by: {symbol: ..., body_hash: ...}
consulted_by: [issue-ppe#check-role, close-timesheet#check-role]
origin: "находка ревью"
```

`requires` образует граф зависимостей решений. У каждого узла графа свой владелец в коде.

## 7. Три слоя

```
BPMN      операции и их шаги
            └─ Business Rule Task ──► decision
Решения   входы, выход, логика, примеры, граф requires
            └─ implemented_by ──► owner_symbol
Код       владелец и sites; места вызова соответствуют задачам BPMN
```

Связующий слой — записи этой модели. BPMN хранится в `.bpmn` со стабильными `process_id#task_id`; записи ссылаются на
эти идентификаторы. BPMN добавляется для операций из нескольких шагов с разными участниками; операции из одного use
case достаточно строки в `consulted_by`.

## 8. Проверки gate

1. **Оракул.** `logic` исполняется как эталон; production-владелец проверяется против него на `examples` и
   property-тестом на границах (полночь по всем поясам).
2. **Согласие операций.** Каждая операция из `consulted_by` на тех же примерах даёт ответ владельца.
3. **Модель → код.** Для каждой задачи из `consulted_by` в графе вызовов use case существует путь до `owner_symbol`.
   Отсутствие пути означает операцию без проверки правила.
4. **Код → модель.** Место, трогающее примитивы или вызывающее владельца без задачи в модели, означает
   недокументированное применение правила.
5. **Устаревание.** Смена `body_hash` владельца переводит запись в `stale` до прогона проверок 1–2. Смена `logic` или
   `examples` поднимает версию решения и сбрасывает вердикты по нему.

Проверки 3 и 4 делают расхождение диаграммы с кодом блокером merge, поэтому модель процессов остаётся актуальной.

## 9. Исполнение проверок и среда

Повторяющийся сбой: участник запускает детерминированную проверку в своей среде, среда расходится с закреплённым
toolchain (инструмент требует Python 3.12, у ревьюера 3.10), проверка останавливается, вердикта нет. Случай
повторяется, потому что знание о препятствии нигде не хранится. Причина та же, что у `date.today()` в разделе 6:
интерпретатор участника служит скрытым входом проверки.

### 9.1. Два класса вопросов

| Класс | Кто выносит вердикт | Ценность независимого повторения |
| --- | --- | --- |
| `deterministic` | инструмент: линтер, тесты, детектор дублирования, gate | нулевая, вердикт является функцией ключа |
| `judgment` | человек или LLM | высокая, второе мнение находит новое |

Требование независимости ревью относится к классу `judgment`. Вердикт класса `deterministic` выносится один раз
авторитетным исполнителем, и все участники вспоминают его по ключу.

### 9.2. Запись `check-verdict`

```yaml
kind: check-verdict
question: gate/duplication@<sha256 профиля>
class: deterministic
anchors:
  tree: <Git tree OID проверенного среза>
  toolchain: <sha256 файла закрепления toolchain>
verdict: green                        # green | red
producer: ci                          # авторитетный исполнитель
evidence: ["ссылка на запуск", "sha256 файла evidence"]
```

Ключ: `tree`, версия вопроса, хеш toolchain. Закрепление toolchain входит в ключ целиком: версия интерпретатора,
ревизия инструмента, дайджест модели эмбеддингов. Вердикт с другим хешем toolchain считается ответом на другой вопрос.

Хранение вне рабочего дерева: статус проверки коммита в CI или `git notes`. Оба способа уже адресованы по SHA, поэтому
ревьюер получает вердикт одним запросом по точному коммиту.

Порядок для участника: поиск по ключу; при попадании вердикт используется как есть; при промахе запуск выполняется
через владельца запуска (9.4) или запрашивается у авторитетного исполнителя.

### 9.3. Три исхода проверки

| Исход | Значение |
| --- | --- |
| `green` | проверка выполнена, нарушений нет |
| `red` | проверка выполнена, нарушения есть |
| `unavailable` | проверка не выполнялась; запись содержит причину |

`unavailable` никогда не засчитывается как `green` или `red` и всегда ведёт к поиску вердикта по ключу. Отчёт участника
разделяет два утверждения: «код замечаний не получил» и «проверка не выполнялась».

### 9.4. Владелец запуска

Разные участники по-разному отвечают на вопрос «как запускается проверка». Это концептуальное дублирование из раздела
5, перенесённое на операционный слой, и решается оно тем же способом:

```yaml
kind: concept
concept: gate-execution
question: "Как запускается проверка X?"
owner_symbol: {path: tools/gate.sh, body_hash: ...}
contract: "единственный вход — корень репозитория; всё остальное владелец берёт из закрепления toolchain"
primitives:
  - invocations: ["python -m <tool>", "<tool> analyze", "python3 <bootstrap>"]
sites:
  - {path: .github/workflows/ci.yml, role: delegates}
  - {path: quality.sh, role: delegates}
  - {path: AGENTS.md, role: delegates}
```

Обязанности владельца:

1. прочитать закрепление toolchain;
2. самостоятельно поднять закреплённую среду, включая интерпретатор нужной версии (`uv run --python <pin>` или
   кэшированный toolchain), без обращения к системному `python3`;
3. до запуска сверить все закреплённые входы: интерпретатор, ревизию инструмента, дайджест модели;
4. при расхождении вернуть `unavailable` с причиной;
5. записать `evidence` с хешем toolchain.

Детектор ищет прямые вызовы инструмента в скриптах, CI и инструкциях агентам. Вызов вне владельца блокирует merge.
Системный интерпретатор участника перестаёт быть входом проверки.

### 9.5. Запись `known-obstacle`

```yaml
kind: known-obstacle
question: "Что мешает выполнить проверку X в среде E?"
anchors:
  toolchain: <sha256 закрепления>
  env: "python=3.10"
symptom: "bootstrap останавливается на проверке версии интерпретатора"
resolution: "вердикт берётся по ключу из CI; локальный запуск идёт через владельца запуска"
occurrences: 2
origin: "отчёт ревьюера"
```

Hook вспоминания показывает запись участнику до запуска проверки. Смена закрепления toolchain переводит запись в
`stale`.

Правило эскалации: второе появление одного препятствия обязано превратиться в структурное исправление — концепт с
владельцем (9.4). Это тот же поток, что «находка ревью → концепт» из раздела 5, с источником «повторный сбой».

### 9.6. Задание участнику

Координатор в задании ревьюеру разделяет два списка: вердикты класса `deterministic`, которые ревьюер вспоминает по
ключу, и вопросы класса `judgment`, по которым ревьюер выносит собственное суждение. Среда ревьюера влияет только на
второй список, а для него достаточно чтения кода.

## 10. Обратное построение модели

Модель строится из кода обратным проходом. Каждый извлечённый элемент процесса хранится как суждение с якорями,
поэтому полная модель обходится дёшево: её никто не ведёт руками, она пересчитывается только там, где сменился хеш.

### 10.1. Два направления авторитета

| Часть модели | Источник истины | Что происходит при `stale` | Размер |
| --- | --- | --- | --- |
| **Описательная** (as-is) | код; элемент модели является суждением о коде | автоматическое повторное извлечение затронутого элемента | полная |
| **Нормативная** (to-be) | модель; код обязан соответствовать | gate краснеет, появляется задание исполнителю | малая, действует критерий входа из раздела 16 |

Нормативный элемент блокирует merge и требует решения владельца, поэтому критерий входа относится только к нему.
Описательная часть покрывает весь код.

### 10.2. Что извлекается

| Источник в коде | Элемент модели | Способ |
| --- | --- | --- |
| точки входа: endpoint, задача по расписанию, обработчик события | операция, стартовое событие | детерминированно |
| граф вызовов use case | шаги операции, обращения к решениям | детерминированно |
| проверки прав и ролей | дорожки (Lane) и исполнители шагов | детерминированно |
| чтение и запись сущностей | Data Object, входы и выходы шагов | детерминированно |
| поле статуса сущности и места его изменения | жизненный цикл сущности: состояния и переходы | детерминированно |
| ветвления по статусу, роли, дате | шлюзы и условия | детерминированно, отбор бизнес-ветвлений выполняет LLM |
| имена шагов на языке предметной области, склейка операций в сквозной процесс | подписи, границы процесса | LLM, класс `judgment` |

Длительный бизнес-процесс не содержится ни в одной функции. Он восстанавливается из жизненного цикла сущности:
состояния, операции-переходы и роли, которым переход разрешён. Это основной приём обратного прохода.

### 10.3. Запись извлечённого элемента

```yaml
kind: process-element
question: process-extraction@v1
class: judgment                      # для детерминированных источников — deterministic
element: timesheet-lifecycle#approve  # process_id#task_id в BPMN
anchors:
  - {path: ..., symbol: ApproveTimesheetUseCase.execute, body_hash: ...}
  - {path: ..., symbol: Timesheet.status, body_hash: ...}
verdict:
  lane: financial-manager
  from_state: submitted
  to_state: approved
  consults: [worker-role-active-at]
evidence: ["путь в графе вызовов", "сценарный тест", "трассы production"]
tier: loose                          # loose | reviewed | confirmed
```

В BPMN элемент несёт ссылку на запись как свойство в `extensionElements`. Новых элементов BPMN модель не вводит.

### 10.4. Верификация извлечённого

1. **Свежесть** — якоря совпадают с текущим кодом.
2. **Структура** — путь в графе вызовов существует, проверки 3 и 4 раздела 8 проходят в обе стороны.
3. **Поведение** — сценарный тест проходит путь процесса; тест указан в `evidence`.
4. **Трассы** — conformance checking по журналам и audit-таблицам production: фактические последовательности
   переходов укладываются в извлечённый жизненный цикл.
5. **Независимость** — второе извлечение другим участником или другой моделью даёт тот же элемент; совпадение
   повышает `tier` до `reviewed`.

### 10.5. Повышение до нормы

Извлечённое из кода описывает историю разработки. Контрактом оно становится решением владельца: элемент получает
`tier: confirmed` и переходит в нормативную часть. Следы в рабочей ветке основанием для повышения не служат;
основанием служат выпущенная версия, данные production или прямое решение владельца.

Обратный проход показывает расхождения как есть: пять мест с разными ответами на один вопрос извлекаются как пять
правил. Такая группа служит кандидатом в концепт раздела 5.

### 10.6. Чего в коде нет

Код содержит способ. Намерение и должное состояние приходят от людей: `reason`, `origin`, решение владельца,
находка ревью. Полная модель складывается из извлечённой структуры и прикреплённого к ней намерения. Разница между
описательной и нормативной частями даёт автоматический gap-анализ AS-IS / TO-BE.

## 11. Инвариант и спецификация

Суждение и инвариант — одна запись, прочитанная в разные стороны. Суждение идёт от кода: «этот код с таким хешем
удовлетворяет X». Инвариант идёт от спецификации: «X должен выполняться; вот чем это доказано». Спецификация —
множество инвариантов с обязательством доказательства. Память доходит до уровня спецификации, когда у каждой
нормативной записи есть `holds_by` и статус доказанности.

### 11.1. Запись инварианта

```yaml
kind: invariant
id: INV-timesheet-approve-role
statement: "Табель утверждает только финансовый менеджер подразделения с активной ролью на момент операции"
refines: [SR-timesheet-approval]          # требование выше по иерархии
uses: [worker-role-active-at]             # решения, на которые опирается
scope:                                    # к чему относится; пусто, пока кода нет
  - {kind: code, symbol: ApproveTimesheetUseCase.execute, body_hash: ...}
holds_by:                                 # доказательства, каждое со своей силой
  - {kind: detector, name: role-check-before-write, strength: static}
  - {kind: test, path: tests/test_approve_requires_active_role.py, strength: property}
  - {kind: judgment, ref: <запись review-verdict>, strength: reading}
status: proven                            # unproven | proven | violated | stale
owner: "владелец продукта"
origin: "требование заказчика"
```

Спецификация пишется до кода: `scope` пуст, `status: unproven`. Список `unproven` в gate служит заданием
исполнителю, как в разделе 13. Появление кода заполняет `scope`, доказательства переводят статус в `proven`.

### 11.2. Лестница силы доказательств

| Сила | Доказательство | Класс | Когда действует |
| --- | --- | --- | --- |
| `static` | тип, детектор AST, правило gate | deterministic | при каждой проверке, для всего кода |
| `property` | оракул, property-тест | deterministic | при каждом прогоне, на генерируемых входах |
| `example` | тест на примерах из `examples` | deterministic | при каждом прогоне, на перечисленных входах |
| `trace` | conformance checking по трассам production | deterministic | по факту, задним числом |
| `reading` | ревьюер или LLM прочитал код | judgment | пока совпадает хеш `scope` |

Ratchet на силу: доказательство инварианта заменяется только равным или более сильным. Суждение класса `reading`
допустимо как временное доказательство и учитывается отдельным счётчиком, который может только уменьшаться.

### 11.3. Иерархия и проекции

```
BR / SR / FR / NFR      требования, текст владельца
   └─ refines           инвариант: проверяемое утверждение
        ├─ uses         решение (раздел 6), концепт (раздел 5)
        ├─ scope        код, документ, схема, элемент BPMN
        └─ holds_by     детектор, тест, трасса, суждение
```

Спецификация, матрица трассируемости и отчёт покрытия — проекции памяти:

| Проекция | Содержимое |
| --- | --- |
| спецификация | инварианты по требованиям с текущим статусом |
| матрица трассируемости | требование → инвариант → доказательство → код |
| покрытие спецификации | требования без инвариантов, инварианты без доказательств, доказательства силы `reading` |
| покрытие кода | код без инварианта; описательная часть из раздела 10 подсказывает кандидатов |

Требование без инварианта — текст без проверки. Инвариант без `scope` — обещание. Инвариант с доказательством силы
`reading` — суждение, которое ждёт замены детектором или тестом.

### 11.4. Связь с суждениями

Каждая ранее описанная нормативная запись выражается инвариантом: концепт — «на вопрос Q отвечает только владелец O»,
решение — «реализация совпадает с `logic` на `examples`», `production-fact` — «поведение P выпущено в версии V».
Суждения остаются формой хранения доказательств силы `reading` и вердиктов описательной части. Итог: две точки
входа в одну память — от кода через суждения и от требований через инварианты.

## 12. Глубина генерации

| Уровень | Что делает модель | Где уместно |
| --- | --- | --- |
| 1. Оракул | проверяет код, написанный агентом или человеком | везде |
| 2. Тесты | `examples` становятся тест-кейсами и property-тестами | везде |
| 3. Проекции | `logic` компилируется в код | решения: маленькие чистые правила |
| 4. Исполнение | движок интерпретирует модель | длинные процессы с ожиданиями и эскалациями |

Сильный случай уровня 3: одно правило живёт в двух формах — предикат над сущностью и фильтр ORM. Формы расходятся при
ручном сопровождении. Компиляция обеих проекций из одного выражения `logic` устраняет этот класс расхождений. Язык
выражений минимален: сравнения, `and`/`or`, `is null`, вызов другого решения.

Процессы остаются на уровнях 1–2. Генерация use case из BPMN повторяет известные проблемы MDA: модель достигает
сложности кода, сгенерированный код закрыт для правок, обратная синхронизация ломается.

Роли распределены так: агент пишет код по модели с учётом окружения и идиом проекта, gate детерминированно проверяет
соответствие. Нормативная часть модели остаётся маленькой: в ней только правила и трассировка. Описательную часть
даёт обратный проход из раздела 10.

## 13. Цикл изменения

1. Запись решения меняется.
2. Версия растёт; записи `implemented_by` и `consulted_by` получают `stale`.
3. Gate краснеет и выдаёт точный список мест: владелец и N операций.
4. Список служит заданием исполнителю: границы, критерий завершения и тесты уже определены.
5. Исполнитель правит код, gate зеленеет, хеши обновляются.

Дифф модели работает как наряд на работу. Координатор команды агентов получает срез для назначения из gate.

## 14. Вспоминание

- Команда `why <path>::<symbol>` показывает все записи по символу.
- Hook на правку файла подкладывает агенту записи по затронутым символам: «у этого вопроса есть владелец», «правка
  инвалидирует 2 принятых решения», «это объединение уже пробовали».

## 15. Жизненный цикл долга

- Отдельный ratchet на число записей `tier: loose`: оно может только уменьшаться.
- Срок пересмотра у принятого долга.
- Повышение `loose → reviewed` требует ссылки на разбор в `evidence`.

## 16. Хранение

Одна запись — один файл с именем по отпечатку, либо JSONL с сортировкой и шардированием по верхним пакетам. Параллельные
агенты перестают конфликтовать при слиянии, а `git log` по записи показывает историю решения.

## 17. Критерий входа

Правило попадает в нормативную часть модели при выполнении одного из условий:

- с ним сверяются две и более операции;
- оно пришло из находки ревью.

Правило одного use case остаётся обычным кодом и видно в описательной части. В нормативной части живут только
действующие правила с заполненным `origin`.

## 18. Порядок внедрения

1. Ступенчатые якоря и статус `stale` для существующих записей.
2. Команда `why` и hook вспоминания.
3. Записи `concept` с детекторами 1–3 для первого системного расхождения.
4. Записи `decision` с оракулом и тестом согласия.
5. Генерация тестов из `examples`.
6. Компиляция `logic` в пару «предикат и фильтр ORM» при появлении второго правила с теми же двумя формами.
7. Кэш `review-verdict` для инкрементального ревью.
8. Владелец запуска проверок, исход `unavailable` и `check-verdict` по SHA коммита.
9. Записи `known-obstacle` с правилом эскалации на втором появлении.
10. Детерминированное извлечение операций, графа вызовов и жизненных циклов сущностей в `process-element`.
11. LLM-склейка сквозных процессов, независимое второе извлечение, повышение до нормы решением владельца.
12. Записи `invariant` с `holds_by`, лестница силы доказательств, проекции спецификации и трассируемости.

## Словарь

| Термин | Значение |
| --- | --- |
| Суждение | решение о коде, вынесенное человеком, ревьюером или LLM |
| Якорь | ссылка на артефакт с адресуемым содержимым: символ кода, раздел документа, элемент BPMN, таблица схемы |
| Вопрос | вид суждения с версией рубрики |
| Концепт | доменный вопрос с единственным владельцем в коде |
| Владелец | символ, который единолично отвечает на вопрос концепта |
| Site | место в коде, трогающее примитивы концепта |
| Решение | формальное бизнес-правило с входами, логикой и примерами |
| Оракул | исполняемая эталонная форма `logic` |
| Инвариант | утверждение спецификации с областью действия, доказательствами и статусом |
| Сила доказательства | `static`, `property`, `example`, `trace`, `reading`; замена только на равную или большую |
| Ratchet | ограничение, при котором метрика может только улучшаться |
| Класс вопроса | `deterministic` — вердикт есть функция ключа; `judgment` — вердикт выносит человек или LLM |
| Владелец запуска | единственная точка входа проверки, которая сама поднимает закреплённую среду |
| `unavailable` | исход «проверка не выполнялась», отдельный от `green` и `red` |
| Описательная часть | извлечённая из кода модель as-is; источник истины — код |
| Нормативная часть | подтверждённые владельцем правила и процессы; источник истины — модель |
| Препятствие | повторяемая причина, по которой проверка не выполняется в конкретной среде |
